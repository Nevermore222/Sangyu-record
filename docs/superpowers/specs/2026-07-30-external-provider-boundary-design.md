# 桑榆录外部 AI Provider 边界设计

日期：2026-07-30

状态：已批准，等待书面复核

默认仓库：`https://github.com/Nevermore222/Sangyu-record.git`

## 1. 文档目的

本文修订桑榆录的系统边界：本项目是回忆录生产流程平台，不建设智能体平台，也不建设共同记忆知识库。媒体模型、知识库和智能体由第三方制品或其他项目提供，本项目通过版本化异步 API 调用这些能力。

本文覆盖 `2026-07-28-ai-memoir-platform-design.md` 中有关以下内容的实现归属：

- 自建共同记忆知识库、向量索引和资料入库。
- Skill 注册、执行沙箱和多语言 Skill Runner。
- 在本仓库内部实现回忆录智能体、提示词和模型运行环境。

旧设计中的采集流程、原始证据不可覆盖、个人记忆与时代背景分离、来源追踪、确定性编排、隐私隔离、异常处理、书稿版本和 PDF 交付原则继续有效。如两份文档发生冲突，以本文的系统边界为准。

## 2. 产品定位

桑榆录负责把线下采集的老人录音、照片和备注可靠地转化为可追踪、可补采、可版本化和可交付的回忆录项目。

本项目的核心价值是：

- 为工作人员提供适合线下采访的采集工具。
- 管理老人档案、授权、原始资料和处理结果。
- 用固定工作流协调外部媒体模型、知识库和智能体。
- 对外部结果执行格式校验、来源校验和本地质量门。
- 管理异常、补采、版本、PDF 和出版社素材包。

本项目不以训练模型、开发通用智能体或积累公共知识资产为目标。

## 3. 系统所有权

### 3.1 本项目负责

- 工作人员小程序和后续运营后台。
- 工作人员账号、项目分配和项目级权限。
- 老人档案、家属联系方式、成书目标和授权记录。
- 首轮采集模板、个性化采集计划和补采轮次。
- 录音、照片、备注、本地暂存、分片上传、断点续传和文件校验。
- 私有对象存储、原始文件不可变规则、指纹去重和派生文件版本。
- 固定工作流、任务队列、状态持久化、超时、重试、取消和局部重跑。
- 外部 Provider 调用、数据最小化、格式适配和调用审计。
- 规范化转写、照片分析、书稿、来源映射和结果版本。
- 异常任务、人工确认、敏感内容状态和补采闭环。
- HTML/PDF 排版、预览、下载和出版社素材包。
- 日志、监控、备份、删除和部署。

### 3.2 外部系统负责

外部能力分为三类：

1. `Media Provider`
   - 语音转写。
   - 说话人区分。
   - OCR。
   - 照片内容理解。

2. `Knowledge Provider`
   - 按年代、地区、职业、生活主题和章节上下文检索共同记忆背景。
   - 返回资料出处、适用范围、可信等级和授权信息。

3. `Agent Provider`
   - 个性化采集计划。
   - 素材完整度评估。
   - 补采计划。
   - 回忆录定位和体量建议。
   - 时间线和章节规划。
   - 分章写作、章节质检和全书一致性检查。

### 3.3 权威边界

- Go 后端是项目状态、工作流状态和交付状态的唯一权威。
- Provider 不能直接连接本项目数据库、队列或对象存储。
- Provider 不能决定下一个业务节点，也不能直接把项目标记为完成。
- Provider 结果必须先经过适配、结构校验和本地质量门。
- 小程序不直接访问 Provider，也不持有 Provider 密钥。
- Mock Provider 仅用于开发、测试和演示，不属于正式 AI 能力。

## 4. 总体架构

首期继续采用模块化 Go 单体和独立 Go Worker：

```text
工作人员小程序
    |
Go Business API
    |-- 项目、授权与工作人员权限
    |-- 采集计划与补采轮次
    |-- 上传会话与私有对象存储
    |-- 异常、书稿版本与成果交付
    |
PostgreSQL <--> Redis / Asynq <--> Go Worker
                                  |-- Media Provider Adapter
                                  |-- Knowledge Provider Adapter
                                  |-- Agent Provider Adapter
                                  |-- 本地质量门
                                  `-- PDF 与素材包生成
```

不增加独立 Integration Gateway 服务。Provider 适配器作为 Go 后端内的清晰模块存在；只有在接入数量、团队边界或部署需求显著增长后，才考虑拆分为独立服务。

现有 `Skill Runner` 将重构为通用 Provider 边界。仓库不再承担 Skill 注册、运行沙箱、多语言执行环境或智能体提示词管理。

## 5. 业务流程

### 5.1 建档与首轮采集

1. 工作人员创建老人项目。
2. 录入基础档案、家属联系人、成书目标和授权范围。
3. 本项目使用本地规则模板生成首轮基础采集单。
4. 如果 Agent Provider 可用，调用 `collection_plan` 补充个性化问题。
5. 外部服务不可用时，基础采集单仍可用于现场采访。

### 5.2 现场采集与上传

1. 小程序完成录音、照片、备注和采访段落标记。
2. 资料先保存在小程序本地安全目录。
3. 上传中心执行分片、校验、暂停、续传和失败重试。
4. Go API 确认完整对象后才把资料标记为已上传。
5. 原始对象不可覆盖，重复处理只生成新的派生版本。

### 5.3 媒体处理

1. Worker 为音频和照片创建外部任务。
2. Media Provider 通过短时、只读链接读取确需处理的文件。
3. 本项目轮询任务状态，并接收签名回调作为加速路径。
4. 返回结果转换为规范化转写段落、说话人、OCR 和照片分析。
5. 低置信度、听不清、人物不确定和文件损坏进入异常任务。

### 5.4 素材评估与补采

1. Agent Provider 执行 `material_assessment`。
2. 本地规则检查人生阶段覆盖、来源密度、冲突和目标篇幅。
3. 素材不足时调用 `followup_plan`，生成下一轮补采清单。
4. 工作人员补充资料后，仅重跑受影响的媒体、评估和下游节点。
5. 达到最大补采轮次仍不足时，系统缩减书籍体量，不虚构内容补足字数。

### 5.5 规划、检索与写作

1. 依次执行 `memoir_positioning`、`timeline_builder` 和 `chapter_planner`。
2. 本项目按章节整理可使用的个人事实包。
3. 按章节年代、地区、职业和主题调用 `shared_memory_retrieval`。
4. 知识库结果独立保存为背景引用，不与个人事实合并。
5. `chapter_writer` 只接收该章事实包、必要的全书摘要和获准背景资料。
6. 每个个人事实引用原始物料；每个时代背景引用知识库条目。
7. 执行 `chapter_review` 和 `book_consistency_review`。
8. 本项目执行不可绕过的本地质量门。

### 5.6 交付

1. 通过质量门的结构化书稿形成不可变版本。
2. 本项目完成 HTML、PDF、缩略图和出版社素材包生成。
3. 工作人员可以预览、下载、创建修订版本和重新生成受影响章节。
4. 下载、重跑和版本切换进入审计日志。

## 6. Provider 异步契约

### 6.1 内部接口

三个 Provider 类型均提供：

```text
Submit(ctx, request) -> external job reference
Status(ctx, external job reference) -> job result
Cancel(ctx, external job reference) -> cancellation result
```

适配器负责把本项目标准请求转换为第三方格式，再把第三方响应转换回本项目标准结构。

### 6.2 推荐外部 HTTP 协议

```http
POST /v1/jobs
GET  /v1/jobs/{provider_job_id}
POST /v1/jobs/{provider_job_id}:cancel
```

任务提交至少包含：

- 本项目 `request_id`。
- 幂等键。
- `task_type`。
- 输入结构版本。
- 期望输出结构版本。
- 结构化输入或短时文件链接。
- 回调地址。
- 截止时间。
- 语言、地区和成书配置。

Provider 返回自身 `provider_job_id`。本项目内部任务 ID 与外部 ID 分开保存。

### 6.3 任务类型

Media Provider：

- `audio_transcription`
- `speaker_diarization`
- `photo_ocr`
- `photo_understanding`

Knowledge Provider：

- `shared_memory_retrieval`

Agent Provider：

- `collection_plan`
- `material_assessment`
- `followup_plan`
- `memoir_positioning`
- `timeline_builder`
- `chapter_planner`
- `chapter_writer`
- `chapter_review`
- `book_consistency_review`

### 6.4 外部任务状态

外部状态统一映射为：

```text
pending_submission
submitted
processing
succeeded
retryable_failed
permanently_failed
timed_out
cancelled
```

回调和轮询可以同时到达；状态转换与结果写入必须幂等。回调丢失时由轮询恢复，Worker 重启时从 PostgreSQL 恢复任务。

### 6.5 标准结果

Knowledge Provider 标准结果至少包含：

- 稳定引用 ID。
- 背景正文或摘要。
- 来源名称和来源位置。
- 适用年份与地区。
- 职业或生活主题。
- 可信等级。
- 授权和允许用途。

Agent Provider 标准结果根据任务类型返回采集项、素材评估、时间线、章节结构、章节内容或质量问题。章节段落必须区分个人事实引用和知识背景引用。

第三方原始 JSON 作为审计附件保存，业务模块不得直接依赖第三方原始字段。

## 7. 数据最小化与访问控制

- 原始音频和照片只保存在本项目私有对象存储。
- 只有对应 Media Provider 获得短时、只读、单任务文件链接。
- Knowledge Provider 只接收检索条件和必要的去标识化章节上下文。
- Agent Provider 默认只接收规范化转写、照片分析、个人事实包和知识库返回内容。
- 智能体不直接读取原始音频和照片。
- Provider 地址必须命中服务端允许列表。
- 密钥来自环境变量或密钥管理服务，不进入小程序和业务日志。
- 回调使用签名、时间戳、请求 ID 和防重放校验。
- Provider 不得依赖未声明的会话状态；每次请求必须可重放。
- 授权撤回后停止未完成外部任务，并按数据策略清理任务关联资料。

## 8. 数据模型

本项目保存业务数据，不建设公共向量知识库。主要实体包括：

- `projects`
- `staff_assignments`
- `consents`
- `collection_rounds`
- `collection_items`
- `assets`
- `upload_sessions`
- `transcripts`
- `transcript_segments`
- `photo_analyses`
- `provider_jobs`
- `provider_attempts`
- `source_references`
- `manuscript_versions`
- `chapters`
- `paragraphs`
- `exception_tasks`
- `artifacts`
- `audit_events`

存储分工：

- PostgreSQL 保存权威业务状态和规范化结构。
- MinIO 保存原始文件、派生媒体、第三方原始响应、书稿快照和产物。
- Redis/Asynq 只负责队列，不作为权威数据源。
- 第三方知识库结果只保存当前项目实际使用的检索快照和引用，不在本项目积累公共知识库。

来源类型继续使用：

- `P`：老人亲述。
- `F`：家属或工作人员补充。
- `I`：照片、证件或实物。
- `K`：外部知识库背景。
- `R`：模型对已有资料的重组表达。

具体个人经历必须至少具有 `P`、`F` 或 `I` 来源。只有 `K` 或 `R` 来源的具体个人经历不能进入最终交付版本。

## 9. 工作人员小程序

小程序是线下采集工作台，不承担 Provider 配置或知识库管理。

### 9.1 页面结构

1. 登录与工作台：分配项目、阶段、待办、异常和更新时间。
2. 创建项目与授权：档案、联系人、成书目标和逐项授权。
3. 项目总览：建档、采集、媒体处理、补采、书稿、质检和交付阶段。
4. 采集计划：按人生阶段和照片任务分组，支持完成、跳过、资料不足和备注。
5. 录音工作台：暂停续录、时长、空间、段落标记和时间点备注。
6. 照片采集：拍照、相册、方向、人物、背面和大致年代。
7. 上传中心：校验、分片、暂停、续传、失败原因和重试。
8. 自动处理进度：使用业务语言展示当前阶段，不暴露 Provider 术语。
9. 异常任务：处理听不清、人物不确定、年份冲突、授权缺失和服务失败。
10. 书稿与成果：章节预览、段落来源、修订版本、PDF 和素材包。

### 9.2 交互原则

- 面向户外、公园和养老院现场，操作目标清晰且便于单手使用。
- 以任务、资料和状态为中心，不采用营销式页面结构。
- 长项目名称、姓名和错误信息换行显示，不挤压操作按钮。
- 录音、上传和阶段控件使用稳定尺寸，状态变化不引发布局跳动。
- 网络恢复后可以续传；删除本地原始文件必须明确确认。
- 小程序只调用 Go Business API。

现有五页小程序是基础验证版本。后续按上述信息架构逐步替换，不继续把所有能力堆叠到现有页面中。

## 10. 本地质量门

以下检查由本项目执行，不能仅依赖 Agent Provider：

- 外部响应符合版本化 JSON Schema。
- 引用的项目、音频时间段、照片和知识条目存在。
- 个人事实至少具有 `P`、`F` 或 `I` 来源。
- `K` 来源只用于时代背景。
- 未解决的年份、人物和授权冲突阻止最终交付。
- 模型文本作为普通数据转义，不能注入 HTML、模板或执行指令。
- PDF 生成前检查章节结构、缺图、空页、文本溢出和敏感内容状态。

## 11. 错误与恢复

Provider 错误分为：

- 可重试：网络中断、限流、临时不可用。
- 不可重试：认证失败、不支持的任务、明确的输入拒绝。
- 业务结果错误：结构不合法、缺少引用或质量不达标。

恢复规则：

- 可重试错误采用有上限的退避重试。
- 不可重试错误立即创建系统异常。
- 业务结果错误保留原始响应，根据任务类型重跑或创建人工任务。
- 单章失败只重跑该章和后续质检。
- 超时任务不能让项目永久停留在处理中。
- 切换备用 Provider 会创建新的处理尝试，不覆盖旧结果。
- 工作人员可以取消、重试和局部重跑，但不能手工伪造成功状态。

## 12. 测试策略

### 12.1 领域单元测试

覆盖项目状态、授权、采集轮次、上传、Provider 任务、重试、版本和来源规则，不访问真实第三方。

### 12.2 Provider 契约测试

使用 Mock Provider 覆盖：

- 提交、轮询、签名回调和取消。
- 超时、限流和临时故障。
- 非法结构、超大响应和版本不兼容。
- 重复提交、重复回调和迟到回调。
- 第三方格式到标准结构的转换。

### 12.3 容器集成测试

使用真实 PostgreSQL、Redis、MinIO、Go API 和 Worker，外部 AI 使用可控 Mock Provider，验证从建档、上传到 PDF 的完整流程。

### 12.4 小程序测试

覆盖建档、授权、录音、照片、弱网上传、补采、异常和成果下载，并在微信开发者工具进行宽窄视口视觉检查。

### 12.5 交付测试

检查 PDF 页数、字体、缺图、空页、文本溢出、来源映射和出版社素材包结构。

## 13. 实施拆分

完整产品拆为独立规格和实施计划：

1. Provider 边界重构。
2. 工作人员、授权和采集基础设施。
3. 媒体处理闭环。
4. 补采与异常闭环。
5. 智能体与知识库编排。
6. 书稿、PDF 与交付。
7. 运营与生产化。

下一份实施计划只覆盖第 1 项：

- 把现有 Skill Runner 概念重构为三个 Provider 接口。
- 建立异步外部任务、任务尝试和标准状态。
- 建立版本化标准请求与结果结构。
- 将现有 Mock Skill 服务重定位为 Mock Provider。
- 用 Mock Provider 跑通当前基础工作流。
- 更新 README、Compose 和验收测试的产品措辞。

该计划不接入真实第三方服务，不实现公共知识库，不实现生产智能体，也不同时扩展完整小程序业务页面。

## 14. 验收标准

Provider 边界重构完成时必须满足：

1. 仓库文档不再表示本项目负责建设智能体平台或共同记忆知识库。
2. Go 代码具有独立的 Media、Knowledge 和 Agent Provider 接口。
3. 所有外部能力采用异步任务和统一状态模型。
4. 第三方原始响应与标准业务结果分开保存。
5. Mock Provider 可以模拟成功、重试失败、永久失败、超时和非法结果。
6. 回调和轮询重复到达时不会重复推进工作流。
7. Provider 不能直接修改项目状态。
8. 原始文件只通过短时只读链接提供给 Media Provider。
9. Knowledge Provider 和 Agent Provider 默认无法读取原始文件。
10. 当前项目创建、上传、工作流和 PDF 验收链路继续通过。
